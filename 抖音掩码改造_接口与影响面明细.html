② 例外：声明是掩码线索，却同时传了 11 位明文号

这种报文一定出现——上游复用一个 DTO、过渡期平台同时下发明文与掩码、链路中途补全真实号码。不能拒收，也不能采信。

号码形态是调用方对「这条线索的号码以哪边为准」的声明。声明为 2，等于调用方自己说：真实号码在平台那边，我传的这个字段不作数。

一旦采信这个明文号，同一条线索就有两个号码源，而这两个源的可信度并不一样。

这里要特别注意：密文同源已经确认（2026-10-17），所以问题不是「对不上」，是「不敢信」。 同源能保证的是——同一个号码，无论谁来算、什么时候算，算出来都是同一个加密标识。它保证不了这个随报文塞进来的 11 位号码本身是对的：可能是上游过渡期为了过校验凑的，可能是占位号，可能是客户早就停用的旧号。

采信它有三个后果：

  • 坐席照着拨，打给的是不确定的人。这个号码没经过平台背书，也没做过在网与空号校验
  • 平台后续正式转明带回真号时，如果与它不一致，主字段会被覆盖一次，前一次通话记录就挂在错的号码上，对账时对不上
  • 一部分老旧模块仍按手机号判重。主字段一有值，这些模块就绕过加密标识走老路，判重口径重新分裂成两套

所以处置不是「怕撞不上」，是「等它被验证过再用」。

2.4 撞重补全：工程前提、审计约束与自测

「同一套算法、一个加密号」这句话，工程上要落成三条，缺一条本节就不成立：

含义 具体指什么 靠什么保证
算出来一样 同一个 11 位号码，本地算与平台下发得到同一个密文 同算法 + 同盐（已确认）
一个号只有一个密文 号码到密文是稳定映射，不随线索 ID、时间、门店、渠道而变 已确认
任意时点可重算 本地随时能对任意明文算出密文，用于反查 加密节点可用

第三条才是真正被依赖的能力：本地把对方线索的明文加密一遍，拿这个密文回自己库里查有没有对应的掩码线索——不向平台发请求，明文不出库。

这条能力是双刃的：谁能调加密节点，谁就能对任意号码算出密文去撞库。因此加密节点只由服务端调用、业务侧不开放直接调用；所有反查必须记操作人与事由，与 2.5 ④ 号码占用检查共用同一套审计约束。

方案口径全部在交底总方案 3.3 路 A：两道闸门（密文同源 / 明文可信）、补的八条规则（补空不覆盖、只写候选、打三标、不并线索、正式链路覆盖并告警、实时 + 日终两个触发点、一条对多条全补、多条对一条取最近一次）、责任归属与三条自我约束，以那份为准，本节不重复。

本节交付给开发的自测清单：① 撞重命中 → 号码落候选明文、主字段仍空、来源=3、状态=0；② 跨店撞重 → 照补（2026-10-21 起不限门店），且能查到「补给了哪个门店」；③ 字节线索主字段已有值 → 一个字不碰；④ 补全后正式链路带回不同明文 → 以正式链路为准，差异有日志、有告警。

灰度：先 dry-run 两周只统计不写，准确率 ≥95% 再开写。同源已确认后，「密文没命中」是正常的查不到；真正要盯的异常是「明明同一个人却算不出同一个密文」，那是加密节点配置漂移，按故障排查，不计入业务拒绝。

这一步防的是「坐席错一位数，正好是另一个真实客户」。看起来概率低，线索量上百万就是天天发生，而且后果是两个客户的数据交叉、两家店抢同一个客户。

LC-B15 落地说明：导入场景下「加密」由谁做、模板怎么改

加密由程序在上传后自动完成，员工不需要、也不该手工填加密标识。 分两种场景：

场景 Excel 里有什么 程序做什么 模板改不改
① 明文号码（常态：展会、门店、DCC 手工收集） 客户姓名 + 11 位手机号 服务端先做 11 位校验 → 本地加密生成加密标识 → 与明文号码同行落库（号码形态记 1） 不用改，员工无感；加密标识由系统生成，不开放填写
② 带掩码的数据（外部系统导出、批量承接字节线索） 手机号列是掩码格式，另有加密标识、原线索 ID 按号码列的形态自动分流：是 11 位明文就走场景①；是掩码格式就走掩码入库，此时加密标识与原线索 ID 必填，缺一个就整行拒收并在结果里标出行号 增加三列可选列：掩码号 / 加密标识 / 原线索 ID；不填就走场景①

两个必须守住的口径：

  • 加密与字节下发同算法同盐，已确认（2026-10-17）。所以场景①本地生成的加密标识，和平台下发的能直接比对：这位客户从手工导入渠道进来，能跟字节来的那条撞上，导入判重成立。原来是这条链上最悬的一环，现在落地了。要守住的是——加密节点必须严格按字节给的算法与盐配置，不许自行选参数或换实现。
  • 导入判重键跟着变：明文行按现有手机号判重不变；掩码行按加密标识（或原线索 ID）判重，同一文件内重复行提示合并，不重复建线索。

3.1 短信：已确认发不出去，影响六处

2026-10-17 答复：掩码号不能接收短信，平台也不代发。 这条定死之后不是「能力打折」，是「抖音线索在拿到明文之前，一次短信都发不出去」。

先确认一件事：短信不是培育任务生成的前置条件——原型《三无忧配置》批次记录可反证：2026-06-15 去重后 10,000 条、短信成功 9,911 条，照样生成 10,000 个任务（同见交底总方案 4.5）。所以抖音线索不会卡在「短信成功」这一步进不来，真正丢的是下面六处的动作：
