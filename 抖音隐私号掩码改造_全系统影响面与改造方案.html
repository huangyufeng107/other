三条写法规矩

  1. 正文叙述一律用中文名，不写英文。 英文名只允许出现在三处：字段定义表、接口对照表、枚举值与错误码。目的是让读的人不必一边读一边记十几个英文串。
  2. 同一个号码，接口层叫「手机号」，存储层叫「主字段」。 报文里没有「主字段」这个概念，所以凡是讲接口入参、讲错误提示，一律说「手机号」；凡是讲主库那一列、讲落库与转正，一律说「主字段」。读的人凭词就知道在说哪一层，不会混淆——phone 这个词在第 2.1 节指接口 A 的入参、在 2.5 节指主库的明文列，同名不同层，是这份文档最容易读错的地方。
  3. B 接口不是 A 接口改个名。 两边字段名不同是历史事实（A 下划线、B 驼峰），不强行统一，但在每张接口表里都成对列出，读者只需要在一处对照。

2.1.3 CB1 落地说明：接口 A/B 的号码字段与校验改造

先统一三个反复出现的词：

  • 撞重：同一个客户从两条不同渠道各来一条线索，系统要认出是同一个人。认出来了叫「撞上」，没认出来叫「撞不上」。
  • 幂等：同一条报文重复推送多次，系统只建一条线索，不重复记。
  • 透传：上游给的字段原样带到下游，中途不改不丢。

③-1 例外：声明是掩码线索，却同时传了 11 位明文号

这种报文一定出现——上游复用一个 DTO、过渡期平台同时下发明文与掩码、链路中途补全真实号码。不能拒收，也不能采信。

号码形态是调用方对「这条线索的号码以哪边为准」的声明。声明为 2，等于调用方自己说：真实号码在平台那边，我传的这个字段不作数。

一旦采信这个明文号，同一条线索就有两个号码源，而这两个源的可信度并不一样。

这里要特别注意：密文同源已经确认（2026-10-17），所以问题不是「对不上」，是「不敢信」。 同源能保证的是——同一个号码，无论谁来算、什么时候算，算出来都是同一个加密标识。它保证不了这个随报文塞进来的 11 位号码本身是对的：可能是上游过渡期为了过校验凑的，可能是占位号，可能是客户早就停用的旧号。

采信它有三个后果：

  • 坐席照着拨，打给的是不确定的人。这个号码没经过平台背书，也没做过在网与空号校验
  • 平台后续正式转明带回真号时，如果与它不一致，主字段会被覆盖一次，前一次通话记录就挂在错的号码上，对账时对不上
  • 一部分老旧模块仍按手机号判重。主字段一有值，这些模块就绕过加密标识走老路，判重口径重新分裂成两套

所以处置不是「怕撞不上」，是「等它被验证过再用」。

处置分五层，一层一层定清楚：

层 处置 为什么
校验 只校验三件套，不校验明文号格式 不因明文号非法而拒收，兼容上游现状
落库 主字段落 NULL；明文值转存候选明文，标注来源「平台随报文带出」，验证状态=0。该列不参与判重、外呼、展示等业务动作，录入与转正规则见 2.5 主字段保持干净，信息不丢
判重 只用加密标识 + 专营店，不读候选明文 与纯掩码线索同一套键，不分裂
展示 显示掩码号；候选明文仅在有权限的详情页以「待验证」标识展示 防坐席照着打
外呼 走隐私号双轨，不拨候选明文 号码未验证，拨出去可能不是本人

候选明文只有一个转正条件：到店转明 / 成交回传的正式链路带回明文并核对一致，才写进主字段，同时把号码来源置为 2，留审计痕迹。转正前不参与任何业务动作。

还有另一条转明路径——跨渠道撞重后，从对方的明文线索补全号码，见 2.4。两条路径的号码来源取值不同（正式链路 2 / 撞重补全 3），审计时能分得开。

不做阻断，但必须留痕：号码形态声明为掩码、却带了明文的报文，按调用方计数上报，推动上游把报文改干净——否则问题会被「兼容」悄悄掩盖。

④ 存储与索引（有一条硬约束）

  • 号码相关字段共 11 列，完整定义只在 2.5 ① 维护一份，本节不重复列表，避免两处口径打架。本节只涉及其中五列：主字段、号码形态、掩码号、加密标识、候选明文。默认值 phone_type=1，其余为 NULL；MySQL 8 用 instant add column，不锁表

  • 候选明文不建索引、不进查询条件——号码占用检查靠密文查 idx_encrypt_id，不靠这个明文列（做法见 2.5 ④）

2.4 撞重之后：把明文号码补回来（另一条转明路径）

前置条件已满足（2026-10-17 字节答复）：我们本地算出的加密标识，与平台下发的是同一套算法、同一把盐，一个手机号只对应一个加密标识。本节从「有条件成立」转为「可执行」；同时解除 2.1 ③-1 与 LC-B15 场景① 的加密口径风险。

「同一套算法、一个加密号」这句话，工程上要落成三条，缺一条本节就不成立：

含义 具体指什么 靠什么保证
算出来一样 同一个 11 位号码，本地算与平台下发得到同一个密文 同算法 + 同盐（已确认）
一个号只有一个密文 号码到密文是稳定映射，不随线索 ID、时间、门店、渠道而变 已确认
任意时点可重算 本地随时能对任意明文算出密文，用于反查 加密节点可用（WP2）

第三条才是本节真正依赖的能力。撞重补全的做法不是「去平台问这位客户是谁」，而是——本地把对方线索的明文加密一遍，拿这个密文回自己库里查有没有对应的掩码线索。整个过程不向平台发任何请求，明文也不出库。

但有边界，得说清：加密标识能本地重算，前提是手里有明文。 所以分两类处理，不能一个脚本扫全表——

线索来源 加密标识丢了怎么办
自有渠道（展会、门店、DMS、垂媒、手工导入） 有明文，本地重算即可补回，可批量跑
字节渠道 手上只有星号和密文，没有明文，本地补不出来。只能按原线索 ID 回头找字节重取，或等正式链路转明后再算

这条能力是双刃的：谁能调加密节点，谁就能对任意号码算出密文去撞库。因此加密节点只由服务端调用、业务侧不开放直接调用；所有反查必须记操作人与事由，与 2.5 ④ 号码占用检查共用同一套审计约束。

字节线索进来时主字段是空的，代价很具体：坐席不能直接拨号，只能走隐私号付费外呼；归属地解析不出来，按城市分配只能落默认城市；短信发不了；报表按号码反查也反查不到。

但只要这位客户以前从别的渠道留过资——垂媒、活动表单、DMS、门店登记——那边就有一条带明文的线索。两条线索靠加密标识撞上，等于拿到了确认书：掩码客户就是那位明文客户。这时把明文补到字节线索上，是最早也最便宜的一次转明，比等客户到店（可能永远不到）实在得多。

三道闸门，全过才补：

闸门 条件 不满足时
密文同源 已确认（2026-10-17）：同一套算法、同一份盐，一个手机号只对应一个加密标识 不再是风险项。但运行期仍要监控「加密标识命中率」，异常下降说明加密节点配置漂移或存量未加密
同一跟进主体 两条线索在同一个专营店（或同一品牌同一门店体系）内 不补。跨店补等于让 A 店看到 B 店客户的号码
明文可信 对方的明文号非空、过 11 位校验、不是掩码形态、在网状态不是空号 不补，继续用掩码

补的规则——是补空，不是覆盖：

  • 只在字节线索主字段为空时写。已有值一律不动，避免两份明文互相打架
  • 写入的是候选，不是主字段：号码落候选明文，主字段继续为空。撞重是技术推断（密文相同），不是客户确认，够不上「已验证」
  • 同时打三个标：号码来源=3（撞重补全）、验证状态=0（待验证）、记下对方的线索 ID（审计要用）
  • 转正走 2.5 的验证与转正流程，与坐席录入共用同一套状态机，不另开一条
  • 撞重只补号码，不合并线索。同一门店内两条线索要不要并成一条，属于重复跟进判断（LC-B3）的事，本节不改变线索条数
  • 补全后若正式链路（到店转明 / 成交回传）带回的明文与此不一致，以正式链路为准覆盖，同时记差异日志并告警——不一致意味着这次撞重可能认错了人，要回查

什么时候补：两个触发点，缺一不可。

触发 做什么 为什么必须有
实时 非字节线索入库时，按加密标识反查同一主体下有没有掩码线索，命中即补 覆盖多数场景，客户当天留资当天可用
日终补跑 T+1 凌晨全量扫一次「有加密标识但主字段为空」的线索 时序错位——字节线索晚到，实时那一跳对方还不存在，只能事后补

三条容易踩偏的口径：

  • 一条明文对多条掩码（一对多拆到 3 家店）：3 条都补，同一个明文，这是对的——它们本来就是同一个人
  • 多条明文对一条掩码（同一个人反复留资）：取最新一次有效留资的明文，不取最早。客户可能换过号，最早的号现在可能已经是别人的
  • 明文之间号码还不一样：同上，以最新为准；旧号不丢，记进撞重审计表供人工核对

灰度与验收：

  • 先 dry-run 两周：开关不开写，只统计「如果开启会补多少条、其中多少条因门店不一致被拒、多少条密文没命中」，准确率达标（建议 ≥95%）再开写。同源已确认后，「密文没命中」就是正常的查不到；真正要盯的异常是「明明是同一个人却算不出同一个密文」，那是加密节点配置漂移，按故障排查，不计入业务拒绝
  • 验收四条：① 同店撞重 → 号码落候选明文、主字段仍空、号码来源=3、验证状态=0 ② 跨店撞重 → 不补，且能查到拒绝原因 ③ 字节线索主字段已有值 → 不覆盖 ④ 补全后正式链路带回不同明文 → 以正式链路为准，差异有日志、有告警

本节的技术地基已经落地（2026-10-17）：字节确认两边同算法、同盐、一个号码一个加密标识，密文可以直接比对，原「不同源则整节作废」的风险解除。剩下要守的是内部纪律——加密节点全系统只能有一个。任何模块私自按另一套参数加密，都会立刻造出对不上的密文，而这种错在数据上不显眼，只会表现为「撞不上」，很难倒查。

④ 号码占用检查：用密文查，不查明文

这一步防的是「坐席错一位数，正好是另一个真实客户」。看起来概率低，线索量上百万就是天天发生，而且后果是两个客户的数据交叉、两家店抢同一个客户。
