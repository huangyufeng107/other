0. 三分钟看懂

0.1 变化本身只有一句话

抖音来的线索，以后没有真手机号了。给的是「带星号的假号 + 一串不可逆的乱码 + 抖音的线索编号」。

后果：判重、坐席搜索、归属地分城、门店分派、黑名单、报表回填——这些动作全部拿手机号当键，键没了，整条链上所有"认人"的地方都要换键。不是"接口加几个字段"。

1. 先统一四个词

开会第一件事，把这四个词对齐，后面所有讨论都靠它们。

词 长什么样 会不会变 拿来干什么
掩码号 *******3090，11 位、前 7 位是星号 固定不变 给人看的（坐席、门店）、兜底外呼的展示号。不能当判重键
加密标识 一串 64 位不可逆乱码（建议预留 128 位） 一个手机号只对应一个，永不变 认人的唯一凭据：判重、黑名单命中、跨渠道撞重全靠它
抖音原线索 ID 抖音自己的线索编号 不变 换可外呼号码的入参；现网查重键本来就是它，直接复用
中间号（外呼临时号） 每次外呼时系统临时分配的号码 每次外呼都会变 只是拨号通道，不能用来认人

一句话记住：号是假的、号还会变，认人只能靠那串乱码。

我方本地算出的加密标识与平台下发的是同一套算法、同一把盐，一个手机号只对应一个加密标识。所以本地密文可以和平台下发的直接比对——这是后面"撞重补全"能成立的前提。

1.1 五条关键判据（读完 480 页原型提炼，判断任何改造点先对这几条）

  1. 同一客户会先后出现在两条链路（先留资线索进主机厂，去重后转培育线索）→ 加密标识必须在两条链路间同口径，否则培育侧把老客户当新客，重复外呼。
  2. 去重不在我方，在 NEV 中台。我方要做的不是自己做跨渠道去重，而是保证标识传到中台、且中台愿意用它。
  3. 号码校验是两道门槛，顺序不能颠倒：车巴巴「13~19 位」在前，线索中心正则 + 在网查询在后。第一道不过，线索根本进不来——所以必须从车巴巴开始改。
  4. 空号检测与在网检测是两套缓存：空号 15 天、在网 48 小时，分别处理、分别降级。
  5. 字节系 11 个入口，号码字段叫法不一、校验强度从"强校验"到"完全没校验"都有：先出映射表再动手，不要一个入口一个入口猜。

2. 改造范围：11 个入口，其实只有 4 个窗口

② 懂车云店线索接口 E2–E5（广告投放 / 日产总部 / 日产店端 / 启辰店端） 电话必填 + 13~19 位（四页一字不差） 对方推送 阻断级：掩码号必然被拦，要按"是不是字节线索"分流校验

2.2 三个结论（直接影响改造顺序）

  • 掩码号在车巴巴这一层就进不来——13~19 位强校验比线索中心的正则更靠前。所以第一批改动必须是 CB9（校验分流），它不改，后面全部无从验证。
  • 查重键本来就是线索 ID（extsystem_clue_id / outSystemCluekey），不是手机号。抖音原线索 ID 直接落到这个字段，不用新建一套判重逻辑——这是个利好。
  • E11 是唯一"没人守门"的入口，拉取型、无校验，要额外确认它会不会把星号当合法电话入库。

3.2 认人：把所有"拿号码当键"的地方换成加密标识

这是改造面最大的一块。逐项清单：

功能 原来拿什么认 改成 不改的后果
重复跟进判断（LC-B3） 手机号查店端跟进中 / 总部处理中 加密标识 同一客户被重复建单、重复外呼
留资未满唯一 ID（LC-B4） 「同一个手机号码自动生成唯一 ID」 加密标识 人群包口径错乱
用户黑名单（LC-B10） 手机号黑名单 加密标识；导入明文先本地加密 黑名单形同失效（最容易漏的一处）
坐席搜索（LC-B6） 精准匹配手机号 加密标识 / 掩码后四位 坐席搜不到人
试驾回访工单（LC-B14） 手机号取 180 天记录 加密标识 历史记录查不出来
一对多拆单（CB2） 一条线索拆给 3 家店 = 3 条独立线索 3 条带同一个加密标识 3 家店把同一人当 3 个新客
首触归因 手机号 加密标识 + 首触打标 渠道归因、投放评估、供应商结算全错
关键行为提醒（同店再次留资 T/N） 手机号 加密标识（时间窗与频次不变） 提醒不触发

两条纪律，违反任何一条整条链就失效：

  1. 加密节点全系统只能有一个。任何模块私自按另一套参数加密，立刻造出对不上的密文——而这种错在数据上不显眼，只表现为"撞不上"，极难倒查。
  2. 密钥轮换必须双向同步（R3a）。字节或我方任一侧换了盐而另一侧没跟，历史密文与平台下发立刻全部对不上，不报错、不告警，只表现为撞重命中率归零。做法：轮换前取 100 条已知明文跑一遍两侧比对，一致再切；命中率跌破基线即告警。

3.3 取真号：只有两条路

号码不能凭空变出来。合规的、技术可行的只有两条：

路 A：撞重补全（成本最低，但要平台书面认可用途）

原理：不去平台问"这位客户是谁"，而是本地把对方线索的明文加密一遍，拿密文回自己库里查有没有对应的掩码线索。明文不出库，不向平台发任何请求。

线索来源 加密标识丢了能不能补
自有渠道（展会、门店、DMS、垂媒、手工导入） 有明文，本地重算即可补回，可批量跑
字节渠道 手上只有星号和密文，补不出来，只能按原线索 ID 回头找字节要，或等正式链路转明

两道闸门，全过才补：

闸门 条件 不满足时
密文同源 已确认（2026-10-17），不再是风险项 运行期监控"加密标识命中率（撞重率）"，异常下降=加密节点配置漂移
明文可信 对方明文非空、过 11 位校验、非掩码形态、不是空号 不补

责任归属：平台对"撞重取得明文"没有官方书面材料，该行为属我方自主行为。因此以下三条需要我方约束：① 只写候选、不写主字段；② 默认不用于外呼取号与对外提供——是否放开由按品牌/门店的策略开关决定，开关默认关；③ 全程审计留痕（含补给了哪个门店）。

补的规则——补空，不覆盖，且只写候选：

先说清楚一条线索长什么样：一条线索就是一行记录，里面有一排格子——手机号（正式栏）、掩码号、加密标识、候选明文、验证状态。下面说的"补"，就是往其中某一格写数。

情形 怎么做 举个例子
抖音线索的"手机号"栏还空着 才把撞出来的号写进去；栏里已经有号的，一个字都不碰 坐席昨天已经手动录过一个号 → 这次不覆盖，免得两个号打架
补进来的号放在哪 写在"候选明文"格——线索里专门放疑似号码的一格；"手机号"正式格继续空着。原因：全系统的外呼、短信、导出都只读正式格，没核实的号放在候选格，天然用不出去 乱码相同只是系统推断，客户本人没确认过；坐席看到的是"疑似号码·待核实"，不是"确认号码"
写入的同时打三个标记 来源=3（撞重补全）、状态=0（待验证）、记下是从哪条线索撞来的 以后报表能把"撞来的号"和"客户自己给的号"分开统计；出了争议也查得到来历
线索条数变不变 不变。只补号码，不合并线索 拆给广州风日、东莞南菱两家就是两条，各补各的；要不要并成一条，是"重复跟进判断（LC-B3）"的事
后来官方回了不一样的号 以正式链路（到店转明 / 成交回传）为准改掉，同时记差异日志并告警；撞出来的旧号不删，进历史表备查 撞出来是 138 尾 8899，到店回传是 139 尾 1234 → 改成 1234，并告警：当初可能认错了人，要回查；8899 留在历史表——也可能只是客户换号了
什么时候补 两个时机都做：① 实时——自有渠道线索一进来，马上撞一次；② 日终——每天凌晨把"有乱码但没号"的抖音线索全扫一遍 客户周一在门店留资，抖音线索周二才进来——周一实时那次它还不存在，只能靠周二凌晨那轮补上。少一轮就漏一批
一条真号对多条抖音线索 每条都补，补同一个号 一条线索拆给 3 家店就是 3 条，3 条都补——本来就是同一个人，不是 3 个人
一条抖音线索对多个历史号码 取最近一次有效留资的号，不取最早的 客户 6 月、9 月、10 月各留过一次 → 用 10 月的；6 月那个号可能已经被运营商回收给别人了。旧号不删，进审计表备查

转正不另开一套流程，走下面"路 B"的验证与转正，与坐席录入共用同一套状态机。

灰度：先 dry-run 两周，只统计不写；准确率 ≥95% 才开写。同源确认后，"密文没命中"是正常查不到，不是异常。

路 B：坐席录入 → 验证 → 转正（不依赖任何外部答复，P0 可先做）

现网《任务跟进》已经允许坐席改号，改完直接盖在号码字段上——不校验、不留痕。掩码上线后这个动作就是"坐席录入真号"的唯一入口，要做的是改它的行为：改号仍可当场拨（那是本次呼叫的会话参数），但不再直接写主字段，改写候选。
